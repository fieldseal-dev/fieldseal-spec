--- Act 6 * Django serves what it can, and refuses the rest ---------------
    adapters throw rather than degrade

    Patient.objects.filter(email="ada@example.com").count()
      -> 1
      Served. Django materializes the §7.4 candidate bucket and
      re-verifies it (spec §7.5) before counting. The Prisma
      adapter refuses the same call -- see act 6's other half.

    Patient.objects.exclude(email="ada@example.com")
      -> FieldsealNotSupported:
         [FIELDSEAL_ERROR] `exclude(email=...)` is not available on an
         encrypted column. The SQL excludes the whole index bucket, and spec
         §7.4 mandates that the bucket holds rows whose value differs -- so
         the query drops rows it should have kept, and they never reach the
         adapter for §7.5 re-verification to put back. A filter's false
         positives are recoverable; an exclusion's false negatives are not.
         Fetch the matches with a positive filter() and exclude their primary
         keys. .candidates() does not lift this: it hands over §7.5, and no
         operation on an exclusion's own result restores a row the database
         already removed (spec §10.2, G24 [#100]).

--- Act 6 * Prisma refuses what it cannot re-verify -----------------------
    adapters throw rather than degrade

    prisma.patient.count({ where: { email: "ada@example.com" } })
      -> FieldsealNotSupported:
         Patient.email: `count` is answered by the database as a COUNT over
         the index bucket. Spec §7.4 mandates that the index bucket holds
         rows whose value differs, so the answer would be computed over rows
         that do not match, and spec §7.5 requires candidates to be decrypted
         and compared before they count as results. Spec §10.2 requires
         rejecting a filter path the interception surface does not reach
         rather than serving it approximately. The extension cannot turn a
         count into a row fetch, so it cannot verify what it counted. Use
         `(await prisma.<model>.findMany({ where })).length`, which counts
         verified rows. If bucket semantics are what you want, say so
         explicitly with candidateScope(() => …) and take on §7.5 yourself.
         (At Patient.where.)

      The Django adapter SERVES this call -- see act 6's other half.
      That is a real capability difference and a designed one: a
      Django manager can materialize the bucket and re-verify it; a
      Prisma extension is bound to the operation it was called for,
      and an operation whose result is a number cannot be turned
      into a row fetch.

    prisma.patient.findMany({ where: { NOT: { email: "ada@example.com" } } })
      -> FieldsealNotSupported:
         Patient.email: negation (`NOT`) is not available on an encrypted
         column. The SQL excludes whole index buckets, and spec §7.4 mandates
         that a bucket holds rows whose value differs -- so the query drops
         rows it should have kept, and they never reach the adapter for spec
         §7.5 re-verification to put back. A filter's false positives are
         recoverable; an exclusion's false negatives are not. Fetch the
         matching rows with the positive form and exclude their ids in
         application code. candidateScope() does not lift this: it hands over
         §7.5, and no operation on an exclusion's own result restores a row
         the database already removed (spec §10.2, decided by G24, [#100]).
         (At Patient.where.NOT.)
