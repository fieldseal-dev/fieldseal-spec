# Django Adapter Technical Specification

**Date:** 2026-08-08 · **Status:** Draft 1 · **Purpose:** the engineering design for `adapters/django` (package `fieldseal-django`), targeting Django 6.1 / 5.2 LTS. Built directly on the verified hook analysis in `docs/04-orm-adapter-notes.md` §1; ORM facts below that were verified there are cited as such, everything else is flagged.

**Conformance target (spec §10.1):** L0 ✅ · L1 ✅ · L2 (a)+(b) ✅ · L3 via documented contextvar side channel ⚠️ · L3-row only with client-generated PKs ⚠️ · L4 ❌.

**Hard rule (spec §11.3 / AD-1):** zero cryptography in this package. The only calls into `fieldseal` are the five sync operations plus `warm`.

---

## 1. Declaration surface

Composition over Django's existing field types — the Rails `encrypts` shape that `docs/04` §8 says to adopt:

```python
from fieldseal_django import Encrypted, BlindIndex, FieldsealMeta

class Patient(models.Model):
    email = Encrypted(
        models.EmailField(),                 # the logical type; drives to_python/validation/forms
        column_uuid="018f3c2e-…",            # REQUIRED, immutable surrogate (spec §6.1)
        index=BlindIndex(                    # optional; presence declares L2
            suite_id=0xFF01,                 # REQUIRED, no default; the suite this index is declared under (§1.0)
            index_id="exact",
            idf="argon2id",
            normalize="nfc-casefold-v1",
            truncate_bits=15,                # §7.4 band for P=100,000 is 9–15 bits; 16 is out of band
            projected_population=100_000,
        ),
    )
    email_bidx = Encrypted.index_column("email")   # explicit sibling column — see §1.2

    class Meta:
        pass

    fieldseal = FieldsealMeta(table_uuid="018f3c2e-…")   # REQUIRED per model
```

### 1.0 The declared suite (`BlindIndex(suite_id=...)`; spec §7.2, §7.8, [#213](https://github.com/fieldseal-dev/fieldseal-spec/issues/213))

A blind-index declaration names its own suite, and the index context's `suite_id` is that declared suite, never the client's write suite (spec §7.2, "The index context's `suite_id`"). The adapter therefore requires `suite_id` on every `BlindIndex`:

- It is **required and keyword-only, and nothing completes it.** A model whose `BlindIndex(...)` states no suite fails startup with E003, naming the model field, and is refused the same way when the client is first built. The Python default is `None`, meaning "not stated": it exists only so that a migration file written before the suite existed still imports (a required argument made every such file a `TypeError` while Django loaded the migration graph, before any check could explain it; PR #282 review). The adapter never fills it from `FIELDSEAL["WRITE_SUITE"]` or from anything else: a default taken from the write suite would recreate the coupling the spec removed, and a later change of `WRITE_SUITE` would then change every index value with nothing raised.
- It is passed through to the core's `IndexDeclaration` unchanged. **Validating it is the core's** (AD-1; §5's "the checks do not re-implement the core's gates"): a non-integer, a bool or an unregistered suite is refused by the core when the client is built, and E003 (§5) reports that refusal at startup. The adapter only adds the model field's name to the message, which the core cannot know; it finds the field by asking the core about each declaration after the client has already failed to build, so a passing startup validates once.
- It is **fixed for the life of the index** (spec §7.8): changing it makes a new index, whose values every row must be re-derived into. Changing `WRITE_SUITE` no longer affects any blind index; it changes only the suite new envelopes are written under.
- It need not be the write suite and need not be on `ALLOWED_SUITES` (spec §7.2). The test model `SuiteTwoDoc` declares `0xFF02` under a write suite of `0xFF01` and is exercised end to end through the ORM (save, equality lookup, stored bytes).
- It reaches migrations: `BlindIndex.deconstruct()` always emits a stated `suite_id`, because it is not a default a later release could change.

**What breaks for existing users.** Every `BlindIndex(...)` on a model must add `suite_id=`; until it does, startup fails with E003. **Existing migration files load unchanged**: a `BlindIndex(...)` serialized without a suite reads as "not stated", and the next `makemigrations` writes an `AlterField` recording the suite . **What that migration costs (measured on the patient-directory demo, Django 6.1.3; reported in PR #282's review and reproduced on the branch):** on PostgreSQL 17 `sqlmigrate` prints `-- (no-op)`; on SQLite 3.53.1 it was a table rebuild (`CREATE TABLE "new__Patient"`, `INSERT … SELECT`, `DROP TABLE`, `ALTER TABLE … RENAME`, `CREATE INDEX`) until [#283](https://github.com/fieldseal-dev/fieldseal-spec/issues/283) (2026-11-18), and is `-- (no-op)` since. The rebuild predated #213 and was not about the suite: `Encrypted.deconstruct()` passed the inner field as a positional argument, two `Field` instances never compare equal, and so the schema editor's `_field_should_be_altered()` was true for two identical `Encrypted` declarations, and SQLite rebuilt the table for every `AlterField` on an `Encrypted` column. See §6, *An `AlterField` that leaves an `Encrypted` column as it is*. Stored index bytes do **not** change when the declared suite equals the write suite that was in use (spec §7.2, *Compatibility*: an index declared with suite `S` derives the bytes a client whose write suite was `S` derived before), so no backfill is needed for a deployment that declares the suite it was already writing under. A deployment whose `WRITE_SUITE` has been changed since its indexes were written must declare the suite those indexes were actually derived under, not the current write suite (this follows from the same *Compatibility* sentence; the adapter cannot detect it, because a stored index value names no suite).

### 1.1 Why explicit UUID surrogates in code

`table_uuid`/`column_uuid` MUST be immutable surrogates, not SQL names (spec §6.1). They are supplied literally in the model source and captured by `deconstruct()` into migrations, so a rename never changes them. The adapter ships a management command `fieldseal_gen_uuids` that prints ready-to-paste values; a system check (E004, §5) fails if any encrypted field lacks one. Deriving them from `app_label.ModelName.field` is forbidden — that is a rename time bomb, exactly what §6.1's justification warns about.

### 1.2 The index sibling column

The blind-index column is a real, explicit field (`Encrypted.index_column`), not a hidden auto-injected one, for two reasons:

1. **Declaration-order clarity.** With an explicit column the order is visible in source, and system check **E001** asserts it at startup. **Corrected at implementation (2026-08-25): the original reason given here was wrong.** This section claimed the index field's `pre_save` "must run after the encrypted field's" because `SQLInsertCompiler.as_sql` iterates in declaration order. Measured: a model with the sibling declared *first* produces the **byte-identical** index value, because `pre_save` reads the instance attribute, which Python set long before any field hook ran. Declaration order cannot affect the index today. E001 is kept for the reasons that are true — deterministic column order in migrations and DDL, readability, and the fact that L3-row binding would make the source's `pre_save` mutate the instance and turn order into a real dependency whose failure *would* be silent. Establishing it now is free; claiming a failure that cannot happen is not.
2. **Migration transparency.** `makemigrations` emits the column with no magic; the operator sees exactly what DDL runs.

`Encrypted.index_column("email")` returns a `BinaryField`-backed field whose `pre_save` reads the *sibling plaintext* off the instance (available — `pre_save` receives `model_instance`, `docs/04` §1) and calls `core.blind_index`. Storage: raw bytes, length `ceil(b/8)`, per spec §7.11 (G8 resolved) — normative now, not interim. The generated column is `BinaryField`, and the adapter's migration check MUST verify the column's collation is binary where the backend allows a text index column at all (§7.11); MySQL is the case that bites, since a `VARCHAR` index column under a `_ci` collation silently matches values the core treats as distinct.

## 2. Value path

| Concern | Design |
|---|---|
| Storage column | `BinaryField` (`bytea`) by default (spec §3.3). Optional `storage="base64"` emits `TextField` with the documented 33% overhead warning at check time (W003) |
| Write transform | Implemented in **`get_db_prep_value`**, not `get_prep_value` — the placement `docs/04` §1 verified as the one both the save path and the lookup path traverse. `pre_save` is used only by the index sibling and for `readonly`-mode write blocking |
| Read transform | `from_db_value` → `core.decrypt` → inner field's `to_python`. Covers `.values()`, aggregates, and `raw()` results (Django decrypts raw *results* — `docs/04` §1, verified) |
| Legacy values in a `binary` column | **Added 2026-10-05 ([#251](https://github.com/fieldseal-dev/fieldseal-spec/issues/251)).** SQLite rebuilds a table for `AlterField` with `INSERT … SELECT`, and a value keeps its storage class, so a column changed from a plain field to `Encrypted(field)` is declared `BLOB` and holds TEXT (`CharField`, `TextField`, `DateField`, `DateTimeField`), INTEGER (the `IntegerField` family, `BooleanField`) or REAL (`FloatField`, and a `DecimalField` value with a fraction; NUMERIC affinity stores a whole-valued decimal as INTEGER) values (measured 2026-10-05, Django 6.1.1, SQLite 3.53.1). The read handed those to the core unchanged, and every pass-through read failed: `TypeError` on a `str` or a `float`, `ValueError` on a negative int, and a positive int became that many zero bytes. The adapter only writes bytes, so a value that is not bytes is never an envelope. In `strict` it is refused unread with the core's `NOT_CIPHERTEXT`. In `permissive` and `readonly` it is read as the inner field read it before the `AlterField` (the backend's converters for the inner field, then the field's own, in the compiler's order) and rendered by the codec, and the core passes those §3.6 bytes through. The UTF-8 of the text would have been right for `string` and `date` only: Django keeps a datetime on SQLite as `2026-10-05 12:34:56.123456`. A value the inner field cannot read raises `FieldsealNotSupported`: text in a `DateField` column that is not a date, or `DateTimeField` text Django's parser cannot take (`not-a-timestamp`, `''`, `2026-02-30 00:00:00`). That refusal still counts as a plaintext read in the core's metric (spec §10.3), which is the cut-over gate, so the rows that fail to render stay visible in it. Text in a `BinaryField` column is refused, not base64-decoded. The rendered bytes still go through the core's recognition, so spec §3.4's stated cost applies here as it does to a legacy `bytea` value: 111 bytes or more starting with `0x02` raises `UNKNOWN_FORMAT_VERSION` in every mode. Postgres `bytea` only ever yields bytes, so none of this runs there. That does not make Postgres safe on its own: there a plain `AlterField` rewrites or refuses legacy values before any read, so `migrate` refuses it and `ConvertToEncrypted` converts a string column instead ([#252](https://github.com/fieldseal-dev/fieldseal-spec/issues/252); see §7). `tests/test_legacy_storage_class.py` |
| Legacy values in a `base64` column | **Added 2026-11-04 ([#245](https://github.com/fieldseal-dev/fieldseal-spec/issues/245)).** A column changed from a plain field to `Encrypted(field, storage="base64")` is declared `TEXT` and holds the legacy text. The read ran that text through a non-validating `base64.b64decode` and handed the decode to the core, so in `permissive` `Zm9v` read back as `foo`, `abcdabcd` and `Anna` raised `FieldsealNotSupported` (their decode is not UTF-8), and `ada@example.com` and `Ada Lovelace` raised a raw `binascii.Error`, which is not a `FieldsealError` at all. The read now decodes the stored text **strictly**. If the decode is an envelope to the core's recognition (spec §3.4), it is decrypted, exactly as before and in every mode. Otherwise the stored text's own UTF-8 is what goes to the core, so spec §10.3 answers for the text as stored: `NOT_CIPHERTEXT` in `strict`, and in `permissive` and `readonly` the core passes it through and counts one plaintext read. This read was checked against spec §3.3, §3.4 and §10.3 and confirmed before it was built. What a pass-through read returns depends on the inner type: a `string` comes back exactly as stored; any other type comes back only when the text is §3.6's canonical rendering of it (`42` in an `IntegerField` column), and is otherwise refused with `FieldsealNotSupported`, still counted, because the core counted before the codec refused. **Added 2026-11-25 ([#299](https://github.com/fieldseal-dev/fieldseal-spec/issues/299)).** The refusal for such a pass-through value says so: the stored value is not an envelope, it is legacy plaintext the core passed through (spec §10.3) that is not the column's §3.6 rendering, and the row needs the backfill or the declared type does not match the legacy column. Only a refusal of a decrypted envelope says the envelope was authentic. Neither message carries the value (spec §9), and both name `Model.field`. Unlike the `binary` row above, nothing is rendered through the inner field's converters, so Django's SQLite datetime text (`2026-10-05 12:34:56.123456`) is refused. A `BinaryField` inner field gets the text's UTF-8 bytes. A value that is not text (SQLite can leave a BLOB in a TEXT column) is not an envelope whatever it holds: refused unread with `NOT_CIPHERTEXT` in `strict`, counted and refused with `FieldsealNotSupported` otherwise. Recognition applies to the operand handed to the core, never to a decode it did not recognize, so a stored text whose decode would be a reserved-version blob (111 bytes or more starting with `0x02`) is passed through rather than raising `UNKNOWN_FORMAT_VERSION`. Spec §3.4's accepted cost applies the other way: a legacy text that is itself the base64 of a valid envelope is read as that envelope. `tests/test_legacy_base64_column.py` |
| Serialization to bytes | The inner field maps to one of spec §3.6's eight logical types, and the value becomes §3.6's canonical rendering of it. The mapping: `CharField`/`TextField` and subclasses → `string`; `BinaryField` → `bytes`; the `IntegerField` family → `int`; `DecimalField` → `decimal`; `FloatField` → `float`; `BooleanField` → `boolean`; `DateField` → `date`; `DateTimeField` → `datetime`. Any other inner field — `UUIDField`, `TimeField`, `DurationField`, `JSONField`, `GenericIPAddressField` — is refused by `Encrypted()` at declaration. The inner field's `get_prep_value`/`to_python` still does Django's input coercion; the bytes are §3.6's, and reads refuse anything but the canonical form. Consequences an application sees: a `Decimal` comes back without trailing zeros (`1.50` → `1.5`, so that equal values index identically); a naive `datetime` is refused on write rather than assumed to be in the default zone, whatever `USE_TZ` says; a `float` handed to a `DecimalField` is refused rather than rounded. Until G25 (#123) this row said the codec used `value_to_string`; it actually used `get_prep_value()` then `str()`, which is CPython's text form, not a specified one. Never pickle (`docs/04` §8, the Rails `Marshal` RCE lesson) |
| `value_to_string` | Overridden so `dumpdata` emits base64 ciphertext rather than **plaintext** into a fixture file (`docs/04` §1 gotcha). It re-encrypts rather than emitting the stored bytes, so a dump is not byte-reproducible, and it needs the tenant context — `dumpdata` over a tenant-bound model outside a `tenant_scope` refuses |
| `loaddata` | **Refused (v0).** Django's deserializer routes fixture values through `to_python`, which also sees user-typed plaintext, so a reloaded fixture's ciphertext is stored and encrypted *again* — the row then reads back as base64 instead of the value, silently. Measured 2026-08-25: text columns corrupted, an `IntegerField` column survived, so the damage is per-inner-type and invisible to a smoke test on the wrong column. `to_python` now refuses a value the core's §3.4 `is_ciphertext` recognizes, in the fail-closed direction only. Moving encrypted data between databases is `tools/backfill`'s job (`docs/15`) |
| Expressions | `QuerySet.update(field=value)` encrypts (hits `get_db_prep_save` — `docs/04` §1 table). `update(field=F(...))`, arithmetic and database functions **raise `FieldsealNotSupported`** — `Field.get_db_prep_save` returns anything with `as_sql` untouched, so silence here would write garbage or plaintext. **Corrected at implementation (2026-08-25): "any expression RHS" is too wide and takes `bulk_update` down with it.** `bulk_update` builds a `Case/When` whose results are `Value(...)` literals, and `Value.as_sql` calls `output_field.get_db_prep_save` on the literal (`for_save=True`), which re-enters the field and encrypts. The refusal therefore tests the *written* expression, not its conditions: `Value` and `Case` trees of `Value`s are served, everything else with `as_sql` is refused. A `When` may reference any column it likes, because that decides which row is updated rather than what is stored in it. **Corrected 2026-09-30 ([#242](https://github.com/fieldseal-dev/fieldseal-spec/pull/242) review): "`Value` … served" was true only of a `Value` whose `output_field` is the encrypted field**, which is what `bulk_update` builds. A `Value("x")` a caller writes resolves to a `CharField`, never re-enters the field, and its literal was stored as **plaintext**, leaving a row that then failed to read (measured on `update()` and `bulk_update()`, SQLite and Postgres). The field now refuses a non-NULL `Value` that does not carry it as `output_field`, and `FieldsealQuerySet` runs that refusal before the statement starts, so it does not leave the caller's transaction marked for rollback |
| `bulk_update` | Supported — routes through `Case/When` with `Value(attr, output_field=field)` which reaches `get_db_prep_save` (`docs/04` §1, verified). Covered by an integration test because the path is subtle. **That was true of the ciphertext only (corrected 2026-09-30, [#240](https://github.com/fieldseal-dev/fieldseal-spec/issues/240)):** `bulk_update` never calls `pre_save`, so an indexed column's index sibling was left as it was and the row could not be found by its new value. `FieldsealQuerySet.bulk_update` now derives the index from each instance and adds the sibling to the statement |

## 3. Query path

### 3.1 L2 (a) — explicit index property

`Patient.objects.filter(email_bidx=plaintext)`: the index field's `get_db_prep_value` derives the blind index from the plaintext parameter through ordinary parameter conversion. Works today with zero rewriting; the query surface is explicit (spec §10 L2(a)).

### 3.2 L2 (b) — transparent rewrite

A registered `Exact` lookup on the encrypted field compiles to a `Col` for the sibling index column (the clean route `docs/04` §1 documents, composing with `Q`, joins, and subqueries):

```python
class EncryptedExact(Lookup):
    lookup_name = "exact"
    def as_sql(self, compiler, connection):
        bidx_field = self.lhs.output_field.fieldseal_index_field
        bidx_col = bidx_field.get_col(self.lhs.alias)
        lhs_sql, lhs_params = compiler.compile(bidx_col)
        rhs = core.blind_index(serialize(self.rhs), bidx_field.fieldseal_ctx)
        return f"{lhs_sql} = %s", [*lhs_params, rhs]
```

`In` gets the same treatment (N index values `IN`'d, spec §7.10).

**Mandatory over-fetch re-verification (spec §7.5) — decided at implementation, 2026-08-26.** The design note this paragraph used to carry is settled as **option C**: `FieldsealQuerySet._fetch_all` re-verifies by default and **`.candidates()`** opts out. The rejected alternative was an explicit `.verified()`, whose failure mode is silent — one forgotten call returns collision rows, which is the §10.2 wrong answer the adapter exists to prevent. The safe path has to be the default path.

**The manager arrives without being asked for.** A default that must be installed by hand is not a default, so `class_prepared` installs `FieldsealManager` on any model with an indexed encrypted column **that declares no manager of its own** — Django marks its own auto-created `objects` with `auto_created`, which is an exact test for "the author did not choose". Where the author did choose, the adapter does not overwrite it; system check **E008** requires them to mix `FieldsealQuerySet` in.

**What re-verification compares is spec §7.5's comparison rule (G19 [#78](https://github.com/fieldseal-dev/fieldseal-spec/issues/78), resolved 2026-08-26 — this adapter was the rule's prototype):** `normalize(stored)` against `normalize(queried)` under the index's own normalizer. The normalizer comes from the core (`fieldseal.normalize`, made public for this); an adapter that reimplemented `nfc-casefold-v1` would be reimplementing portability surface where a disagreement is a silent lookup miss.

**The design work is not the rewrite, it is what shrinks.** Verification drops rows *after* the database has applied `COUNT`, `LIMIT` and `OFFSET`, so every queryset method answered from SQL is wrong by default. Each is handled explicitly:

| Surface | Behaviour on a verifying queryset | Why |
|---|---|---|
| iteration, `list()`, `len()`, `bool()` | verified | all route through `_fetch_all` |
| `count()`, `exists()`, `first()`, `last()` | **implemented correctly** | materialize and verify; `exists()`/`first()` stop at the first verified match. Cost is bounded by the bucket, which §7.4 sizes at `2 ≤ P·2^−b < √P` by design |
| `get()` | **implemented correctly** | Django's `get()` samples `LIMIT MAX_GET_RESULTS` (21) of the *candidates*, so a §7.4 bucket larger than the window could hold the true match past it and raise `DoesNotExist` about a row that exists. Verified `get()` materializes the whole bucket (found in the PR #79 review round) |
| `iterator()`, `aiterator()` | **verified, still streaming** | both bypass `_fetch_all` by design (no result cache), so the stream is filtered as it passes. `aiterator` is the one async method that does not delegate to its sync twin; every other `a*` method wraps the overridden sync one, and the test suite pins that |
| `filter(field=None)`, `__isnull`, `exclude(field=None)` | **served exactly, no verification needed** | NULL plaintext stores NULL in both columns and Django rewrites `exact=None` to `isnull`, so the SQL is `IS [NOT] NULL` on the envelope column itself — precise, touches no blind index, allowed in any combination including negation and `OR` |
| slicing / pagination / `qs[i]` | **refused** | LIMIT/OFFSET precede verification, so the page is short and the next one misaligned — and `qs[i]` is `LIMIT i,1`, the `first()` failure behind different syntax. §7.5 states outright that pagination built directly on an indexed encrypted column is incorrect; the documented pattern is over-fetch → decrypt → filter → paginate |
| `earliest()`, `latest()` | **refused** | `LIMIT 1` applied by the database before verification — `first()`'s failure behind another name; the message points at `.order_by(f).first()` |
| `update()`, `delete()` | **refused** | the statement runs in the database against the bucket, so it would write to or destroy rows whose value differs. The only unrecoverable case on this list |
| `aggregate()` | **refused** | answered from SQL, over candidates |
| `values()`, `values_list()`, `only()`, `defer()` | **refused** | they decide which columns come back, and verification needs the encrypted one |
| `exclude()` | **refused** | the SQL excludes the whole bucket, so it drops rows it should keep and they never reach the adapter for §7.5 to put back. **A filter's false positives are recoverable; an exclusion's false negatives are not.** This is not Django's rule: spec §7.10 carries the row and §10.2 the adapter obligation, both added by G21 [#87](https://github.com/fieldseal-dev/fieldseal-spec/issues/87) after the same reasoning had to be rediscovered for Prisma's `notIn:`. **`.candidates()` does not lift it, and the message no longer recommends it** — G24 [#100](https://github.com/fieldseal-dev/fieldseal-spec/issues/100), 2026-09-06 |
| `Q` with `OR` over an encrypted column | **refused** | a candidate may be present because another branch matched, so verification cannot decide it without evaluating the whole predicate in Python. A **plain AND of positive terms** records obligations and verifies exactly like keyword arguments — under AND, every returned row must satisfy the encrypted term too, so per-term verification is exact. `.candidates()` lifts this one: a wider bucket can only *add* rows to an `OR` |
| `Q` negated (`~Q`, `exclude(Q(...))`) or `XOR` over an encrypted column | **refused, and `.candidates()` does not lift it** | the same false-negative asymmetry as `exclude()`, one row up. XOR is here because it is negation once expanded — `a XOR b` is `(a AND NOT b) OR (NOT a AND b)`, so a widened bucket flips rows *out* of the answer. The negation is tracked in its own slot rather than read off the verification reason, because under `filter(Q(x) | ~Q(enc=v))` the enclosing `OR` claims that slot first and the negation would never be seen (G24, [#100](https://github.com/fieldseal-dev/fieldseal-spec/issues/100)) |
| subquery embedding (`__in=qs`, `Subquery`, `Exists`) | **refused, at two layers** | the subquery runs entirely in the database, where §7.5 cannot run, so the outer query would receive unverified candidates — silently. `resolve_expression` catches the one route where Django resolves the *queryset*; `Exists(qs)` and `Subquery(qs)` take `qs.query` in their constructor and never call it, so a second layer walks the expression tree wherever such a wrapper can appear — a positional `filter()`/`exclude()` argument, an expression child of a `Q`, a keyword operand, `annotate()`/`alias()`. Found in the G24 review round: every one of those had been reaching SQL unrefused, in **both** directions (a verifying queryset's bucket served as the answer, a `.candidates()` one under `NOT EXISTS` dropping the collision row). Escape: materialize verified pks, or embed `.candidates()` **in a positive `filter()`** — a subtractive position is refused there too, see below |
| `union()`, `intersection()`, `difference()` | **refused, on either side** | the combined statement is answered by the database, and this queryset's obligations cannot be applied to rows the *other* operand contributed — the AND-composition argument only holds within one WHERE clause. `.candidates()` lifts `union()` and `intersection()` and **not** `difference()`, which is G24 applied to set operators rather than a second rule: widen the bucket and the first two return *more* rows, the third returns fewer |
| relation traversal (`filter(rel__enc=...)`, forward or reverse) | **refused, at two layers** | the join matches the blind-index sibling, but §7.5 runs on the queryset that owns the column: a `FieldsealQuerySet` refuses at `filter()` time, and the lookup itself refuses at compile time for **every other queryset** — a related model with a plain manager never passes through this package's queryset at all, so the field layer is the layer that actually holds (PR #79 review round). Escapes: `filter(rel__in=Owner_qs.filter(col=v).candidates())` for bucket semantics, or verified primary keys. **A negated traversal is refused as a negation, not as a traversal** — the position check runs first, because the compile-time backstop passes by design when the column's owner is the querying model (a self-FK, an MTI parent, a round trip out and back), which is where that ordering let a wrong answer through until the G24 review round |

`.candidates()` lifts the *verification* refusals in that table — including the filter-time `Q` under `OR`, since the SQL semantics they refuse are exactly what it hands over — and returns bucket semantics, documented as unverified. An escape hatch that refuses the same things is not one.

**It does not lift negation, and that changed here: G24 [#100](https://github.com/fieldseal-dev/fieldseal-spec/issues/100), decided 2026-09-06 in the Prisma adapter's direction.** This adapter lifted `exclude()` and its refusal message recommended doing so; spec §10.2 now forbids both. The deciding argument is what the caller can do with what they were handed: under `filter(...).candidates()` they hold a *superset* of the answer and reach it by dropping rows — that is §7.5, and handing it over is the entire point of the hatch — while under `exclude(...).candidates()` they hold a *subset*, and no operation on it restores a row the database already removed. The hatch was transferring a responsibility that is not dischargeable from what it transferred with it. **`XOR` came in on the same test** and was not in the issue's filing: `a XOR b` is `(a AND NOT b) OR (NOT a AND b)`, so a widened bucket drops rows from it exactly as an exclusion does. The refusal is by *position*, not by operator — spec §10.2 states it that way — and `IS [NOT] NULL` is outside it, reading the envelope column's own null-ness with no bucket involved.

**Position also means a position the bucket is only an *operand* of, and the closure did not cover those (G24 review round, 2026-09-08).** `exclude(pk__in=Owner.objects.filter(col=v).candidates())` names no encrypted column in the outer predicate and subtracts the whole bucket; so do the relation form, `difference(…candidates())` and `annotate(has=Exists(…candidates())).filter(has=False)`. All four were measured served, with the colliding row dropped. `resolve_expression` cannot hold this line — it is handed the operand without the position, so it cannot distinguish these from `filter(…__in=qs.candidates())`, which is exactly what the traversal and cross-model messages recommend. The queryset therefore marks its own `Query` (`fieldseal_indexed` / `fieldseal_verify`, which survive the clone `Subquery.__init__` takes) and the position is read at `filter()`, `exclude()`, `difference()` and `annotate()`. A `.candidates()` queryset that never touched an index is **not** a bucket and embeds anywhere: the rule is about the semantics, not the method name.

**Refusal honesty on a column with no bucket (G24 review round, item 5, 2026-09-08).** The refusals in this section justify themselves with §7.4 bucket mechanics — an exclusion drops the whole bucket, a database-answered operation computes over one, an `OR` branch leaves a candidate §7.5 cannot decide — and each is checked *before* the column is checked for having an index at all. On a column with no `BlindIndex`, or under a lookup §7.1 keeps off the index, that justification described a bucket that is not there, and the remedy it prescribed (run the positive form instead) is refused on its own account. **The check order is deliberate and unchanged**: reversing it sends a caller to run a schema migration for a shape that is refused *with* the index too. So the fact travels in the message — the refusal names the real reason first, keeps the position rule as an explicitly counterfactual second half, and points at the fallback that works either way (fetch, then filter after decryption). Spec §10.2 states this principle as two instances rather than one clause — the G23 bytes-computation sentence and the G24 escape-hatch sentence — and this is a third instance implemented without one.

The other refusal it cannot lift is the cross-model traversal, because another model's queryset cannot take on §7.5; the opt-in there is the *owning* model's `.candidates()`, embedded as above.

**`filter()` was not the only door, and every rule in this section lived behind it (G24 review round item 1, [#118](https://github.com/fieldseal-dev/fieldseal-spec/issues/118), 2026-09-08).** Two routes reached the blind index without passing `FieldsealQuerySet._filter_or_exclude`, so §7.5 obligation recording, the `OR` refusal and the G24 subtractive refusal were all simply absent on them. **`complex_filter(Q)`** calls `query.add_q` directly — Django's own body routes only the *dict* form through `_filter_or_exclude` — so `complex_filter(Q(email=v))` served the bucket as the answer, `complex_filter(~Q(email=v))` dropped it, and `complex_filter(Q(email=v) | Q(…))` served what the `OR` refusal exists to stop; all three measured. **`Model._base_manager`** is a plain `Manager` returning a plain `QuerySet` — Django builds it that way deliberately, so its own internals are not filtered by a custom default manager — so on the *owning* model there is no queryset layer at all, and the compile-time traversal backstop passes there by design, because the owner **is** the querying model; no unusual method was needed, an ordinary `filter()` was enough. Neither route is one a caller has to type: Django applies `limit_choices_to` through `complex_filter` at five sites, two of them on `_base_manager`, so an ordinary `full_clean()` and a `ModelForm`'s choice list both arrived here.

**The fix is one per layer, deliberately not one per entry point** — an adapter enumerating Django's doors is the failure mode this was an instance of. `complex_filter` is overridden with the same walk `filter(Q(…))` runs, which is the half that needs queryset state. The other half moves down to `_IndexedLookup`, beside the cross-model backstop and by the same argument one relation shorter: **an encrypted equality compiles only for a query whose rows a verifying queryset will materialize and re-verify — or one whose caller took §7.5 on with `.candidates()`.** `FieldsealQuerySet` marks its `Query` at birth as well as on every clone, and the refusal reaches only predicates that touch the index, so `_base_manager` keeps answering primary keys, `IS [NOT] NULL` and unfiltered reads, which is what Django's own FK validation, cascade collection and `refresh_from_db` need from it.

**Two distinct ways to fail that, and the first cut only checked one (found by this PR's review round, 2026-09-08).** The first is the *absence* of the mark — no queryset of ours ever held this `Query`, which is what `_base_manager` builds. Note the asymmetry that makes the check work: `fieldseal_verify = False` is a caller opting out with `.candidates()` and stays served, while the attribute *missing* is nobody having opted in. The second is a mark that is real but belongs to the wrong query: `Exists(qs)` and `Subquery(qs)` take `qs.query` and never touch the queryset again, so the lookup compiles for an *inner* query carrying a genuine mark while the rows are fetched by an enclosing statement that may have no layer at all. Measured with a forged collision: `_base_manager.filter(Exists(objects.filter(pk=OuterRef("pk"), email=v)))` returned the §7.4 bucket and the `exclude()` form returned G24's subtractive wrong answer — so the shape the first check refuses was rewritable as a correlated `Exists` and served. The second check keys on `Query.subquery` together with `fieldseal_verify`, and on `verify` alone rather than `verify and indexed`, because §7.5 runs over rows the queryset materializes and a subquery's rows never leave the database, whatever its index mark says. `FieldsealQuerySet` already refuses this embedding at `filter()`/`annotate()` time, which is why the same subquery under a verifying *outer* was refused before; this is that rule at the layer the enclosing querysets that never reach the first one still pass through.

**The residue, stated rather than claimed away.** A `.candidates()` bucket in a *subtractive operand* is refused on any `FieldsealQuerySet` by the bucket-as-operand rule above, and from `Model._base_manager` there is nobody to read the position. It has **two spellings, and the compile-time layer misses each for its own reason** (the second was raised on this PR's re-review round). `exclude(pk__in=Owner_qs.candidates())` never reaches that layer at all: the outer predicate is on a plain column and the operand is a queryset, so no `_IndexedLookup` compiles anywhere in the statement. `exclude(Exists(Owner_qs.candidates()))` *does* reach it — an indexed lookup compiles inside the subquery — and is allowed through deliberately, because `fieldseal_verify` is `False` there and the boundary check must not refuse the embedding three refusal messages recommend; the lookup is handed the operand without the position, which is the same argument `_refuse_bucket_operand` exists for one layer up. Both are served, short by the collision. That is the same residue this section already records for a model with no encrypted column of its own, with the owning model's plain manager as a second instance; it stays a residue rather than a hole for the same reason, which is that the caller had to construct the bucket deliberately to arrive there. Both spellings are asserted as residues in the test suite so that neither can drift back into a claim.

**One route the issue did not list, found writing the tests.** `forms.models.apply_limit_choices_to_to_formfield` wraps the condition in `Exists(…)`, which the subquery-embedding rule above refuses — but on Django 6.1 it builds that subquery from **`_base_manager`**, so the embedded queryset carries no `fieldseal_indexed` mark and the expression walk never sees one. Measured before the fix: a `ModelForm` over a FK whose `limit_choices_to` names an encrypted column offered the §7.4 collision row as a valid choice. It is door 2 wearing door 1's clothes, and the lookup-layer refusal is what closes it — which is the argument for putting the backstop below the entry points rather than at them.


**The G20 family ([#80](https://github.com/fieldseal-dev/fieldseal-spec/issues/80), closed 2026-08-26; discriminator narrowed to bytes-reading by G23, [#89](https://github.com/fieldseal-dev/fieldseal-spec/issues/89)): SQL that reads envelope bytes.** A second refusal family, orthogonal to §7.5 verification and active on **every** `FieldsealQuerySet`, obligations or none — a meaningless order needs no filter present to be wrong — and **not lifted by `.candidates()`**: bucket semantics are a meaningful thing to accept for a filter; ciphertext order has no semantics to accept. Measured before the refusals were written: `order_by("email")` returned envelope-byte order; `values("email").annotate(n=Count("pk"))` returned four groups of `n=1` where the truth was three with one `n=2`, two groups printing the identical key; **`aggregate(Min("age"))` over `{30, 40}` returned `40`** — the byte-wise minimum *envelope* decrypts cleanly to an arbitrary row's value, presented as the minimum, with nothing raised.

| Surface (any `FieldsealQuerySet`) | Behaviour | Why |
|---|---|---|
| `order_by()` naming an encrypted column — direct, `-`-prefixed, through a relation, or inside an expression (`F("email").asc()`, `Lower("email")`) | **refused** | sorts envelope bytes; §7.10 ciphertext row |
| `earliest()`/`latest()` naming one, or falling back to a `Meta.get_latest_by` that names one | **refused** | the same ordering through a different door (`add_ordering`, never `order_by()`) |
| aggregate or function expressions **that read envelope bytes**, referencing an encrypted column in `aggregate()`, `annotate()`, `alias()`, `values()` | **refused** | `MIN()`/`MAX()` return an arbitrary envelope's value decrypted and presented as the extreme; `SUM()` produces garbage misreported as `NOT_CIPHERTEXT`; `COUNT(DISTINCT)` counts envelopes; `LENGTH()` reports ciphertext size |
| a plain, non-distinct `Count(field)` over an encrypted column | **served** (G23, [#89](https://github.com/fieldseal-dev/fieldseal-spec/issues/89)) | reads null-ness, never envelope bytes: under §10.2's NULL-preservation invariant the count over envelopes equals the plaintext count exactly. The bare shape only — `distinct=True` and an inner function (`Count(Length(...))`) fall back to the bytes refusal; a `filter=` form is refused with its own stated reason (the carve-out is the plain shape, and `.filter(<cond>).aggregate(n=Count(field))` is the same count), never with a false bytes claim; on a queryset *filtered by* an encrypted column the §7.5 SQL-answered rule still refuses. `filter(f__isnull=False).count()` is the same count as a WHERE-clause spelling, not a workaround |
| an encrypted column inside a condition the queryset's filter path never sees — an aggregate's `filter=`, a `When.condition` (in `aggregate`/`annotate`/`alias`/`values`/`order_by`/`earliest`/`latest`) | **refused** (found and closed in the G23 closure's review round) | those `Q`s resolve when the *expression* compiles, not when `.filter()` runs, so the lookup arrives without §7.5 obligations: an equality compiles to an index-bucket match that is never re-verified. **Measured before the refusal existed**: `Count("created", filter=Q(email=…))` was served and returned bucket counts, and a `When(email=…)` branch fired on a bucket match — both silently. `iter_reference_names` cannot see into a `Q` (a tree of `(path, value)` tuples, not an expression), which is why the condition walk is separate |
| `values(...).annotate(<aggregate>)` with an encrypted column in the projection | **refused** | the projection becomes the `GROUP BY`: one group per row, wrong counts under identical printed keys |
| `distinct("field")`, or `distinct()` over a `values()`/`values_list()` projection naming an encrypted column (either call order) | **refused** | every envelope is distinct; deduplicates nothing, silently |
| a bare `F("email")` annotation | **allowed** | it only *selects* the column, and the converter decrypts what comes back — exact |
| bare `distinct()` on full model rows | **allowed** | the projection includes the primary key, so every row is already unique — a full-row `SELECT DISTINCT` cannot dedupe wrongly on envelope bytes, only no-op. (§7.10's ciphertext-column row is about computing *on the column*; this shape never asks the envelope bytes to carry identity) |
| `order_by("email_bidx")` (the index sibling) | **allowed** | deterministic, documented as meaningless — a stable tiebreaker |
| `Meta.ordering` / `Meta.get_latest_by` naming an encrypted column | **system check E009** (Error) | the compiler applies both directly, where no queryset refusal can see them |
| an encrypted column the admin changelist would order by | **system check W005** (Warning) | `ModelAdmin.ordering` breaks every changelist request; a sortable column breaks on a header click — both now raise, so the check says so at startup |

**Interception honesty (`docs/04` §1):** Django resolves ordering names to a plain `Col` with no field hook in the path, so the refusals are queryset-level plus the two checks — which means a *plain-manager* model ordering through a relation onto another model's encrypted column is not reachable, unlike the equality traversal, which is closed at the lookup layer. That residue is documented in the raw-SQL class.

The same honesty applies to the bucket-as-operand rule above: the position is read on a `FieldsealQuerySet`, so a model with **no encrypted column of its own** has no queryset of ours to read it from and `Plain.objects.exclude(fk__in=Owner_qs.candidates())` is not reachable. Unlike the equality traversal there is no lookup-layer backstop to fall to, because the outer predicate is on a plain column; unlike ordering, the caller had to construct the bucket deliberately to get there. It is a documented residue, not a covered case.

### 3.3 Refused lookups (spec §10.2 — throw, never degrade)

On the encrypted field, every lookup except the rewritten `exact`/`in` (and `isnull`) raises `FieldsealNotSupported` with the honest-fallback text from spec §7.10: `contains`, `icontains`, `startswith`, `gt/gte/lt/lte`, `range`, `regex`, `iexact` (case folding belongs to the normalizer, not the query — and since G19 ([#78](https://github.com/fieldseal-dev/fieldseal-spec/issues/78), resolved 2026-08-26) that is spec §7.5's normative rule rather than an aside: §7.5 re-verification compares normalized values, so on a `nfc-casefold-v1` column `exact` **is** the caseless lookup and a second one would be a second equality the index cannot serve), `search`. Without a declared index, `exact`/`in` raise too ("no blind index declared for this column").

## 4. Context assembly and modes

- `FieldContext` per column is built once at `contribute_to_class` time (table/column UUIDs, suite from settings). Tenant: `fieldseal.django.context.set_tenant(tenant_id)` contextvar, with a shipped middleware example; documented as the L3 side channel of spec §10 — including that any code path outside the middleware scope (management commands, celery tasks) must set it explicitly or encryption fails closed (`ConfigurationError`), never silently falls back to tenantless context when a tenant-bound column is declared.
- `row_id` binding: not in v0 of the adapter. Django cannot see the PK at INSERT with identity keys (`docs/04` PK table); L3-row support arrives only for models the check system can prove use client-generated PKs (`default=uuid7`-style) — deferred, tracked in the coverage matrix as ❌ with the reason.
- Read mode has exactly one owner: `settings.FIELDSEAL["READ_MODE"]` feeds the client the **adapter constructs** (§7) — there is no second mode knob, and the client is immutable after construction (docs/09 §2), so a mode change is a process restart. `permissive` and `readonly` warn while active (the core's `FieldsealWarning`, raised when the client is built), and count plaintext reads per model and field (spec §10.3 requires the warning and SHOULDs the metric). **Built 2026-11-18 ([#246](https://github.com/fieldseal-dev/fieldseal-spec/issues/246));** until then this sentence promised a signal nothing sent, and the only count was the core's `Fieldseal.plaintext_reads`, one integer for the whole client. `fieldseal_django.signals.plaintext_read` is sent once per value the core passed through, with `sender` the concrete model that owns the field (`field.model`: for a field inherited from an abstract base, the subclass) and `field` its name, never the value; `fieldseal_django.signals.plaintext_read_counts()` returns `{(model label, field name): reads}` for the current client: the counts are kept per client object, as the core's count is, so a rebuilt client starts both at zero, a `FIELDSEAL["CLIENT"]` instance (which `reset_client` hands back unchanged) keeps both, and while the adapter is the client's only reader the counts sum to its `plaintext_reads`. **The counts are per process**, like the core's: a `manage.py shell` started to check the gate has its own client and reads `{}`, and each worker of a multi-process server holds its own share, lost when the worker is recycled. A count over a deployment and a window is the signal exported to a shared metrics backend, not `plaintext_read_counts()` read in one process. Both follow the core's count exactly: they fire after `decrypt` passed a non-envelope operand through, and before the codec renders it, so a value the codec or the inner field then refuses (`FieldsealNotSupported`; §2's legacy-value rows) is counted and signalled as the core counts it ([#253](https://github.com/fieldseal-dev/fieldseal-spec/issues/253)), and a read the core refuses (`NOT_CIPHERTEXT` in `strict`, `UNKNOWN_FORMAT_VERSION` in every mode) is neither. The count is reads, not rows: a legacy value read twice counts twice, and the backfill's own in-place reads (§7) count too, so a window for `PROCEDURE.md` §8's cut-over gate should not overlap an `encrypt` run. In the two-column shape the `Encrypted` column only ever holds NULL or envelopes, so its count stays at zero throughout and says nothing about that shape's progress: the census does. The count is taken before the signal is sent, and the signal is sent with `send_robust`: a receiver's exception is not raised and the read goes on, because a failing metrics client would otherwise turn every legacy row into an error, and every in-place backfill row into `INTERNAL`. **Changed 2026-11-19 ([#295](https://github.com/fieldseal-dev/fieldseal-spec/issues/295)):** until then every failure of a receiver was logged at ERROR with its traceback, twice: by the adapter on `fieldseal_django` and by Django's own `send_robust` on `django.dispatch` (measured, 50 reads through one raising receiver: 100 ERROR records, 50 on each). Now only a receiver's **first** failure is logged, once, by the adapter (ERROR, with `exc_info`; the message says later failures are counted, not logged). "First" is per receiver object while it lives (held weakly, so a freed receiver is forgotten), for the client that made the read, so two instances of one class are each logged once. Django's per-failure log is switched off for this signal: `plaintext_read` is an instance of a private `Signal` subclass that overrides `Signal._log_robust_failure` (present in Django 5.2.19 and 6.1.3). That hook also reads `receiver.__qualname__`, so without the override a receiver with none (a `functools.partial`, a callable instance) raised out of `send_robust` and failed the read. The override is private Django API; a test fails if `Signal` stops having it. A receiver's name in the accessor is its function (a `functools.partial`'s wrapped function) or its type, never its `repr`. "A receiver cannot break a read" holds for synchronous receivers and for `async def` receivers called outside a running event loop: from a thread with a running loop, an `async def` receiver makes Django's own `send_robust` raise `RuntimeError` (AsyncToSync; reproduced on Django 6.1.3), which is not caught. And `fieldseal_django.signals.plaintext_read_receiver_failures()` returns `{receiver name: failures}` for the current client, the logged first failure included. The name is `f"{module}.{qualname}"` (the `repr` when the receiver has none), so receivers that share one dotted name (two instances of one class) are summed under it, each still logged on its own first failure. The failures are kept per client object, as the plaintext-read counts are: a rebuilt client logs a failing receiver again, and a `FIELDSEAL["CLIENT"]` instance keeps them across `reset_client`. Absent when zero, empty with no client, a copy, and per process like the counts. The Prisma adapter follows the same rule for `onPlaintextRead` ([#298](https://github.com/fieldseal-dev/fieldseal-spec/issues/298), `docs/13` §3). `strict` pays nothing for this: a successful strict read is always an envelope, so no second recognition runs.

## 7. Async, warm-up, and operations

- All field hooks are sync; Django's async ORM wraps sync (`docs/04` §1) — so the DEK cache is mandatory, and the adapter's docs say so in bold. **Implemented 2026-08-26**, with one deliberate departure from the sentence this bullet used to carry. `manage.py fieldseal_warm` primes the cache for every declared column, and the `AppConfig.ready()` hook exists but is **opt-in** (`FIELDSEAL["WARM_ON_READY"]`) rather than automatic: `ready()` runs for `makemigrations`, `shell`, `collectstatic` and every test process, so warming unconditionally would make a command that touches no encrypted row pay a KMS round trip — and fail when the key service is unreachable, so a migration could not run because of it. **A migration blocked by a cold KMS is a worse failure than a cold cache.** The honest consequence is documented instead of defaulted around: under an `EnvelopeKeyProvider`, §8.2 confines unwrapping to `warm` and forbids the value path from blocking on network, so **something** must warm the cache before the first read — the setting or the command, with no third option and no silent fallback that would make a cold read work. A warming failure at `ready()` warns and continues, because a web worker that exits on a transient KMS blip takes the deployment down for a condition the next request might not have. The one exception is a `FieldsealWarning` that the deployment escalated, which is re-raised (see the hooks bullet below).
- **Warming covers index keys, not just data keys.** Spec §5.2 makes the index key a *sibling* of the tenant DEK rather than something derived from it, so a cache warmed only for the data key still stalls every indexed lookup — and the symptom looks like a slow query rather than a cold cache. **Tenant-bound columns need their tenants named** (`--tenant`, or `FIELDSEAL["WARM_TENANTS"]`): a tenant-bound context carries a `tenant_id`, and the adapter cannot enumerate a deployment's tenants, which live in application data under a schema this package knows nothing about. A run that omits them names the columns it skipped rather than reporting a warm cache it did not warm.
- Settings surface and client construction: `FIELDSEAL = {"KEY_PROVIDER": callable, "CLIENT": callable, "READ_MODE": …, "ALLOWED_SUITES": […], "WRITE_SUITE": …, "ARM_PROVISIONAL_SUITES": bool, "WARM_ON_READY": bool, "WARM_TENANTS": […], "ON_WARNING": callable, "METRICS": object}` — that is the whole set (`_SETTING_KEYS` in `apps.py`), and an unknown key is refused at startup rather than ignored. There is deliberately **no `CACHE` key**: the §5.5 policy belongs to the envelope provider (docs/09 §2, §8.3), so a deployment wiring an `EnvelopeKeyProvider` hands it its `CachePolicy` inside the `KEY_PROVIDER` callable. The **adapter constructs the `Fieldseal` client** in `AppConfig.ready()`, after model loading, assembling the `IndexDeclaration` registry from the model-level `BlindIndex(...)` declarations — that is the only way the core's construction-time validation (docs/09 §2: §7.6 gate, §7.4 band) runs against the indexes actually declared on models. Escape hatch: `FIELDSEAL["CLIENT"]` (callable returning a pre-built client) for deployments that must own provider wiring, gated by system check E006 — its index registry must exactly match the model declarations, or startup fails.
- **The core's hooks, `ON_WARNING` and `METRICS` ([#306](https://github.com/fieldseal-dev/fieldseal-spec/issues/306), 2026-11-25).** Both are passed to `Fieldseal(on_warning=…, metrics=…)` as they are, and the core validates them (`docs/10` §4); the adapter repeats no rule. `ON_WARNING` receives the core's `FieldsealWarning`s (`StaticKeyProviderWarning`, `ReadModeWarning`) instead of `warnings.warn`; a handler that raises makes the warning a hard failure out of client construction (`docs/09` §8.2), reported by `manage.py check` as E010. The client is built on first use, so outside the checks that failure arrives on the first request that touches an encrypted field, not at process start, unless `WARM_ON_READY` finds contexts to warm and so builds it in `ready()`. There the escalated warning is re-raised and stops the process, although any other warming failure warns and continues: it is the deployment's request for a hard failure, not a transient condition. `MetricsHookWarning` is not routed to it: the core always reports a failing metrics hook through `warnings`. The adapter's own report of a failing `plaintext_read` receiver stays on logging (§4). `METRICS` is an object with `plaintext_read()` and/or `decrypt_error(code)`. Its `plaintext_read()` is called for exactly the reads the `plaintext_read` signal reports, at the same point, without the model and field, so with the adapter as the client's only reader its calls, `plaintext_reads` and the sum of `plaintext_read_counts()` agree; neither feeds the other, and a deployment wiring both into one backend counter counts each read twice. `decrypt_error(code)` has no adapter equivalent. **Either key with `CLIENT` is refused** (E007, and `FieldsealConfigurationError` at first use): `build_client` returns a supplied client without reading other keys, so the hook would change nothing, silently. The other keys `CLIENT` makes irrelevant (`KEY_PROVIDER`, `READ_MODE`, the suites) are still ignored with it, as before; that is not changed here.
- Migration/backfill: the procedure is `tools/backfill/PROCEDURE.md` (`docs/15-tooling.md` §1), following the dual-write shape of `docs/04` §11, and the adapter ships its Django frontend, `manage.py fieldseal_backfill` *(corrected 2026-10-03; this bullet used to say the adapter ships nothing beyond field defaults)*. Built: `init`, `encrypt`, `resume`, `abandon`. Not built: `rotate`, blocked on a header accessor no core exports ([#241](https://github.com/fieldseal-dev/fieldseal-spec/issues/241)), and `verify`.
  - **Shapes (`PROCEDURE.md` §6.1 leaves this statement to the binding doc).** *Two columns*, a legacy plaintext column named with `--source FIELD=LEGACY_FIELD`, is supported for every column. *In place* is supported for `storage="binary"`, where the column's legacy bytes are already the spec §3.6 rendering of the value, and for `storage="base64"`, where the column's legacy text is the value as stored (§2, *Legacy values in a `base64` column*; [#245](https://github.com/fieldseal-dev/fieldseal-spec/issues/245)). Either needs `READ_MODE = "permissive"`. **On Postgres a plain `AlterField` into `bytea` does not produce the `binary` state, so `migrate` refuses it** ([#252](https://github.com/fieldseal-dev/fieldseal-spec/issues/252), decided 2026-11-18). Django converts with `USING col::bytea`, which reads text as `bytea` input: a backslash escape or a leading `\x` is decoded without error (`a\101b` becomes `aAb`, `\x41` becomes `A`), and other backslashes fail the migration. Every non-string type fails it as well, except the integers on Postgres 18. Those become their big-endian bytes, which the read usually refuses. But an integer whose bytes are ASCII digits reads back as a different integer with no error: 825373492 is stored as `1234` and read as 1234 (measured 2026-10-05 on 17.11 and 18.6). The field cannot change that cast: Django's Postgres schema editor decides the `USING` clause in `_using_sql`, from the two fields' data types alone. So `fieldseal_django.operations` ships two things. (1) **`ConvertToEncrypted`**, an `AlterField` with the same arguments and the same state change, used in place of the one `makemigrations` writes. On Postgres it converts a `varchar` or `text` column whose inner field is a `CharField` or `TextField` with `USING convert_to(col, 'UTF8')`, the value's UTF-8 bytes, which are spec §3.6's `string` rendering, and back with `convert_from(col, 'UTF8')`, which fails loudly on a value that is not UTF-8, as an envelope is likely to be. So unapplying it is for a column nothing has written to through the field yet: one `save()` after the conversion stores an envelope, and the rollback then fails and leaves the column `bytea` (pinned by a test). Everything else `alter_field` does stays Django's, including dropping a `CharField`'s `_like` index before the type change. On SQLite it is a plain `AlterField`. On Postgres it refuses any other inner type unless the column is already `bytea` (a `BinaryField` into `Encrypted(BinaryField())`, which needs no conversion), and it refuses any backend other than these two, which are not measured. It never merges with a later `AlterField` of the same field when migrations are squashed, which would leave a plain `AlterField` from the plain field, and a later `RenameField` of the same field is moved ahead of it without changing its class (Django 5.2's `AlterField.reduce` rebuilds the operation as a plain `AlterField`; 6.1 keeps the subclass). (2) **A `pre_migrate` receiver** that, on Postgres, refuses the whole plan before any DDL runs if a plain `AlterField` would change a column between `bytea` and another type with an `Encrypted` field on either side, in either direction, including one in a `SeparateDatabaseAndState`'s database operations. Out of `bytea` the cast writes `\x…` hex text, so this covers unapplying such a migration, and a `BinaryField` changed into `Encrypted(BinaryField(), storage="base64")`, where `AB` would be stored as the text `\x4142`. The receiver checks each operation against the state Django's executor will use: the applied migrations and then the plan, in the full plan's order (for a rollback, every applied migration ahead of the one being unapplied, other branches included), over the same graph `migrate` planned with (without replacements when the target is a migration a squash replaced). A model Django would not migrate on the database (unmanaged, proxy, swapped, or routed away, with the `model` hint) is skipped as Django skips it. The message names `ConvertToEncrypted` for a string column into or out of `binary` storage and the two-column shape otherwise. The receiver also raises a `ConvertToEncrypted`'s own refusal (an `IntegerField` inner field, say) before the plan starts, rather than when that migration runs after earlier ones in the plan have committed: every refusal on Postgres and SQLite, and on any other backend the declaration's own (two `Encrypted` declarations, or `base64` storage). **Every other inner type has no in-place route into a `binary` column on Postgres,** except a `BinaryField` column, which is `bytea` already: a non-string type's text form is not §3.6's rendering and the integer cast is not either, so use the two-column shape. **Costs, stated.** `ConvertToEncrypted` replaces the schema editor's private `_using_sql` for the one field it alters, and a test pins that method's signature. That test protects this repository's CI, not an installed Django (the dependency is `django>=5.2`), so the operation also refuses at run time when `alter_field` returns without having consulted the replacement: a Django that kept the method but stopped calling it would have run its own cast. The raise is inside the migration's transaction, so the `ALTER` rolls back with it, except in a migration with `atomic = False`. `migrate --fake` over a plain `AlterField` of this kind is refused too, because `pre_migrate` does not say the run is fake. So is `--fake` over a `ConvertToEncrypted` whose declaration is wrong (two `Encrypted` sides, or `base64` storage) on any backend, or whose inner type has no conversion on Postgres. On a backend that is not measured, the backend's own refusal stays with the operation when it runs, so `--fake` can record a column converted there by hand (pinned by a test). A column converted by hand should be recorded as a `SeparateDatabaseAndState` with the conversion in a `RunSQL`, which the receiver lets through as the operator's statement that the conversion was done. On a fresh database, test databases included, a historical plain `AlterField` of this kind is refused although the table is empty; edit that migration to use `ConvertToEncrypted`. `sqlmigrate` is not guarded: for a plain `AlterField` it still prints Django's cast, so SQL applied by hand from it is not protected. The receiver walks the full plan once per `migrate` whose plan has an `AlterField` in it on Postgres, or on any other backend an `AlterField` to an `Encrypted` field (which covers `ConvertToEncrypted`; the identity check of #288 needs an `Encrypted` declaration on the new side), as `migrate` itself does, and renders the project state once more for each operation it refuses. Measured on Postgres 17.11 and 18.6 with UTF-8 databases. `convert_to` and `convert_from` name the encoding, so on 17.11 a LATIN1 database stores `Zoë` as `\x5a6fc3ab` and restores it, and in an SQL_ASCII database a value that is not UTF-8 fails the conversion with the column unchanged (measured in SQL, 2026-11-18). **Not guarded:** a cast done outside an `AlterField`, such as a `RunPython` that calls `schema_editor.alter_field` or a third-party operation that does not subclass `AlterField`; and `MigrationExecutor.migrate()` called directly, which sends no `pre_migrate`, as `migrate` sends none when no installed app has a models module. A project's own `AlterField` subclass that already converts correctly is refused like a plain one; the receiver checks a `SeparateDatabaseAndState`'s database operations too, so record it as a column converted by hand: the `AlterField` in the state operations and the conversion in a `RunSQL`. A `base64` column is `text`: from a `varchar` or `text` column a plain `AlterField` leaves the legacy text as it is, and from a `bytea` column `migrate` refuses it, as above. In place on a `base64` column was refused at start until 2026-11-04, because the adapter's read decoded legacy text as base64 before the core saw it (`Zm9v` read back as `foo`, [#245](https://github.com/fieldseal-dev/fieldseal-spec/issues/245)). It now converts a `string` column's text as stored. A non-string column converts only text that is §3.6's canonical rendering; any other row is recorded as `RENDERING_REFUSED` and left as it was (`PROCEDURE.md` §6.3), so for a `DateTimeField` column holding Django's SQLite form (`2026-10-05 12:34:56.123456`) use the two-column shape. On SQLite a plain `AlterField` leaves the legacy values in their old storage class (TEXT, INTEGER or REAL inside a column declared `BLOB`), and in place converts them through the adapter's read of such values (§2, *Legacy values in a `binary` column*; [#251](https://github.com/fieldseal-dev/fieldseal-spec/issues/251)). A value the inner field cannot read is recorded as `RENDERING_REFUSED` and left as it was.
  - **How a batch is spelled.** One `transaction.atomic()` block; the stored bytes come from a raw `SELECT … FOR UPDATE` on Postgres, because `values()` and `raw()` both decrypt; on SQLite the command refuses to run unless the connection's `transaction_mode` is `IMMEDIATE`. The legacy value is read in place by `Encrypted.from_db_value` on the bytes the batch locked, which is the adapter's permissive read applied to them (this is a reading of `PROCEDURE.md` §6.3 rule 1, which asks for the adapter's read "of that row and column"), and in the two-column shape by `values_list()` on the legacy column. That read and every write go through a `FieldsealQuerySet` built on the model, not through its default manager: a default manager may filter rows out (soft delete), the batch's raw `SELECT` does not, and a row selected but hidden from the write would be left as plaintext. Every write is `bulk_update` on that queryset, one value per call inside a savepoint, so a value the codec or the index refuses fails alone (backfill MUST use `bulk_update`, never `queryset.update(F(...))`).
  - **Tenant-bound columns (`PROCEDURE.md` §5.5, version 2; [#244](https://github.com/fieldseal-dev/fieldseal-spec/issues/244), 2026-11-18).** The adapter takes the tenant from a context variable (§4), not from the row, so `encrypt` takes `--tenant FIELD`: a field of the same model that holds each row's tenant, used for every tenant-bound column of the run, and recorded in `config` as each such column's `tenant`. A run with a tenant-bound column and no `--tenant` is refused at start, and so is `--tenant` on a run with none. The field may be an integer, UUID, `CharField`/`TextField` or `BinaryField` column, or a `ForeignKey` to one, rendered as §5.5 says: an integer as its decimal digits, a UUID as lowercase hyphenated text, text as its UTF-8 bytes, binary as it is. **That has to be what the application passes to `set_tenant` for the row** (§5.5, §2 item 5): `set_tenant(str(request.tenant.pk))` matches an integer or UUID key; `set_tenant(tenant.uuid.bytes)` does not, and such a table cannot be backfilled under version 3. The tenant is read in the batch's locked `SELECT`, and each tenant-bound value's write, and in place its permissive read, run inside `tenant_scope()` with that row's tenant, so a tenant the process had bound is never used. (In the two-column shape the legacy column is read for the whole batch by `values_list()`, outside any scope: it is plaintext, and the read needs no tenant.) A row whose tenant field is NULL or empty, or holds a value of another storage class than the field's type (SQLite, after an `AlterField`; §2), is recorded as `CONTEXT_UNAVAILABLE` and left as it was. `resume` takes no `--tenant`: it reads the column from the run's `config`, and refuses if the live declaration no longer matches it. Before version 2, every tenant-bound value was recorded as `CONTEXT_UNAVAILABLE`.
  - **Per-column counts (`PROCEDURE.md` §3, §4, version 3; [#291](https://github.com/fieldseal-dev/fieldseal-spec/issues/291), 2026-11-19).** A third state table, `fieldseal_backfill_columns`, holds each run's five value counts per column, inserted with the run row and updated in each batch's commit, so a new `encrypt` run's comparison with earlier runs is per column for a version-3 run: a column a run covered but never wrote (a tenant-bound column whose tenant column was NULL on every row, say) no longer fixes its tenant column or index declarations, and abandoning the run releases it. `init` creates the table on a database that has the first two and alters none, and every subcommand but `init` refuses to run until it exists. A version-2 run has no per-column count and is still compared per run, so a multi-column version-2 run can still hold a column it never wrote (`PROCEDURE.md` §12). A new `encrypt` is refused first, naming the run, while any run on the table is `running`, since that run could still write a column the per-column comparison skipped; a version-3 run whose column counts do not add up to its own is compared per run and warned about, not refused. The report gives each column's counts.
  - **In place on PostgreSQL needs `--acknowledge-in-place-conversion`** (`PROCEDURE.md` §6.1, §9 item 6). The columns this adapter names under §6.1 are every in-place column on PostgreSQL. Into `binary` storage, Django's cast rewrites legacy text ([#252](https://github.com/fieldseal-dev/fieldseal-spec/issues/252)); into `base64` storage from `bytea`, it writes the bytes as `\x…` hex text. `migrate` refuses both as plain `AlterField`s, but not a conversion done outside an `AlterField` or by hand-applied `sqlmigrate` SQL (*Not guarded*, above), and the run cannot tell how a column got its type. So a new run over such a column, on a table with rows, prints the procedure's text and the columns, and starts only with the flag. The flag is the operator's statement that the column was converted by `ConvertToEncrypted`, recorded as converted by hand (`SeparateDatabaseAndState` with a `RunSQL`, above) by a conversion that keeps the value, or already had a type that holds the value as it is; it is not a check. SQLite does not need it: a plain `AlterField` there leaves the values as they were (§2).
  - **Limits.** A single-column primary key of an int, UUID or text type. Replication-lag throttling is not implemented; the command says so at start. The rate defaults are `PROCEDURE.md` §5.3's and are unmeasured.

## 8. Test plan

**The index half, 2026-08-31 (`cross/v2`; `cross/v3` since #213).** The producer also emits *index* cases (seven since #213): the blind-index sibling column as the database holds it, plus the declaration read off the model's own `BlindIndex(...)` rather than restated. **Since #213 the document is `fieldseal-vectors/cross/v3`** (`docs/08` §4.7) and every declaration carries `suite_id` (a string such as `"0xFF01"`), taken from the **validated declaration the client reports** (`Fieldseal.indexes`), not from a constant or the write suite. The `suite-ff02` case is the one that tells the two apart: `SuiteTwoDoc.handle` is declared under `0xFF02` while the document's suite, the key and every envelope are `0xFF01`, so a consumer that substituted its own write suite derives a different index and fails it. A consumer in another language re-derives each one. This is the half `docs/07` §7 calls the more valuable assertion — a mismatched index is a **silent lookup miss**, so the row stays stored and decryptable and simply stops being findable, and the envelope half stays green through it. The case only an adapter can produce is the last: a value `nfc-casefold-v1` refuses, where the field stored the §7.2 reserved marker by itself because `Person.legal_name` declares `on_unindexable="bucket"`. A core alone cannot demonstrate that — it has no column declaration and no write path.

- **Path matrix tests:** one integration test per row of §6, against Postgres and SQLite in CI (binary column behavior differs; both are supported targets).
- **Refusal tests:** every §3.3 lookup and every 🛑 row asserts the typed exception, not a generic error.
- **Ordering regression:** a model with index-before-encrypted declaration must fail E001; a model without the check bypassed must produce correct sibling values under `bulk_create`.
- **Candidate re-verification:** seed two plaintexts that collide at the configured truncation length (construct via brute force at small `b` in the test), assert the collision row is filtered out.
- **Permissive-mode metric:** plaintext read increments the signal exactly once per value. **Built 2026-11-18 (#246):** `tests/test_plaintext_read_signal.py`, in `permissive` and `readonly`, holds the signal and the per-field counts to the core's `plaintext_reads` read for read: an envelope, a `strict` refusal and a reserved version in a `binary` column are none (in a `base64` column a stored text whose decode is a reserved version is passed through and counted, `test_legacy_base64_column.py`); a value the codec refuses is one. The legacy-value suites (`test_legacy_storage_class.py`, `test_legacy_base64_column.py`) assert the per-field count beside every core-count assertion, which covers the two refusal paths that hand the core an empty operand. `test_backfill.py` pins that the in-place backfill's reads count, and that a receiver that raises converts every row anyway. **Added 2026-11-19 (#295):** `test_plaintext_read_signal.py` pins the failing-receiver rule: N reads through a raising receiver give one `fieldseal_django` record with `exc_info` and `plaintext_read_receiver_failures() == {name: N}`, the reads still return their values and the counts still match the core's; two raising receivers give one record each; a rebuilt client logs again; a supplied client keeps its failures across `reset_client`; the value is in neither the record nor the count. Every logging assertion counts ERROR records on all loggers, not only `fieldseal_django`, so Django's own `django.dispatch` log cannot come back unseen. Also pinned: a `functools.partial` and a callable-instance receiver cannot break a read, two instances of one class are logged once each (accessor `{name: 2N}`), `django.dispatch.Signal` still has `_log_robust_failure`, a weakly connected bound method of each of two instances is logged once (`weak=True`, which resolves a fresh bound method per send), receivers freed and replaced are each logged and leave no state behind, a `functools.partial` carrying a secret keyword argument is named for its function and the secret is in no record, and a receiver whose `__repr__` raises cannot break a read.
- **Cross-language sharing test (the point of the project) — implemented 2026-08-26.** `adapters/django/tests/cross_produce.py` writes rows through the **real ORM path** (real `save()`, runtime CSPRNG, no test-mode injection), reads the raw column back through a database cursor, and emits a standard `fieldseal-vectors/cross/v1` document. **Every existing consumer reads it unmodified**, so the adapter joins the N×N matrix as one more producer — `django` is now a third value of the `cross-produce` matrix, and both core consumers take `cross-django.json` alongside the others.

  **What this covers that no core test can.** Three decisions between an application value and the stored column belong to the adapter: the **codec's rendering** (`IntegerField(45)` becoming `b"45"` — a choice until spec §3.6 pinned it, and pinned now by the `codec/` vectors (`docs/08` §4.8), which this adapter runs; a consumer expecting another encoding would decrypt successfully and read the wrong value), the **storage form** (`binary` versus `base64`), and **context assembly** from model declarations plus the tenant contextvar (a consumer reconstructing it differently gets `COMMITMENT_INVALID` — a decrypt-side error for a write-side configuration mismatch). A core round trip sees none of them.

  The local suite runs the producer and decrypts it with a client built **independently** from `vectors/keys/`, so a case passes only if the stored bytes are readable from the shared key material alone. The true cross-language leg needs Node and therefore runs in CI. Two runs must also disagree on every envelope, since a producer that had drifted onto the injection seam would otherwise pass everything (spec §4.4).

It is the more valuable assertion of the two, because a mismatched index is a silent lookup miss rather than an error, and it needs the `cross/v1` schema to carry the index declaration. Tracked as the next cross-language increment rather than half-done here.

## 9. Deliberate non-goals

No transparent `row_id` binding (v0), no query support beyond `exact`/`in`/`isnull`, no admin search integration, no automatic tenant inference from the request (explicit contextvar only), no support for `Encrypted` on relational fields (`ForeignKey` stays plaintext — spec §7.10), no Django < 5.2 support.

## 10. Unindexable values (docs/09 §7.2 — normative for this adapter)

`encrypt` does not normalize and `blind_index` does, so a value containing a code point the pinned Unicode version does not define **stores but cannot be fingerprinted**. Every `Encrypted*` field carrying an index therefore declares `on_unindexable`, and the adapter's behaviour follows from it. This section is the obligation `docs/09` §7.1 refers to; it is normative for this adapter, and it is the reason `refuse` is a default rather than the only option.

### 10.1 What the adapter does

| `on_unindexable` | Write path | Query path |
|---|---|---|
| `refuse` (default) | `blind_index` raises `INVALID_ARGUMENT`; the field raises `ValidationError` from `to_python`/`get_prep_value` so the failure arrives as a **form error on that field**, not a 500 | A lookup for such a value raises the same `ValidationError` — never returns an empty queryset |
| `bucket` | The sibling index column receives the column's reserved marker; the row saves | A lookup derives the same marker, matches the bucket, and §7.5 re-verification narrows — no adapter special-casing |

`refuse` MUST surface as a field-level `ValidationError`, not as a generic 500 or a silently dropped index. A `ModelForm` then renders it beside the offending input, which is the only place the person who typed the value can act on it.

**Where the refusal is raised is load-bearing, and was corrected at implementation (2026-08-26).** The index can only be derived in `pre_save`, which is the one field hook that receives the instance — and `pre_save` runs *inside* the INSERT, so a `ValidationError` raised there propagates out of `Model.save()`, whose `transaction.atomic(savepoint=False)` marks the connection for rollback. The caller then has their field error **and a transaction they cannot use**, which is not a form error in any sense that helps. The check therefore also lives in `Encrypted.validate()`, which `full_clean()` calls — so the `ModelForm` path fails before the database is touched, and `pre_save` remains the backstop for code calling `create()` directly. That second path still marks the transaction; it is Django's behaviour for every exception in `save()` rather than something this adapter chose, and it is documented in the package README rather than pretended away.

**One implementation note that costs an hour to rediscover:** `ValidationError` **discards `code` and `params` when its message is a dict**. The machine-readable half has to be carried by the inner error — `ValidationError({field: ValidationError(msg, code=..., params=...)})` — and a caller who builds the dict itself loses it with no warning that it did.

### 10.2 The message (normative in shape, not in wording)

"Unsupported character" fails every part of this. The message MUST:

1. **Name the specific character and where it is.** The user cannot act on "somewhere in this field".
2. **Put the fault on the system.** The value is not invalid — it is a name, and the system's tables are out of date. Wording that implies the user made a mistake is wrong on the facts.
3. **Offer a route that ends with the real value stored.** A refusal with no escape hatch is a dead end for the person on the other side of it, which is why `refuse` and `bucket` are specified as a pair: `bucket` is the operator-applied escape hatch, not an alternative philosophy.

```
We can't save this name yet. Our systems don't recognise the character 𠮷
(3rd character). This is a gap on our side, not a problem with your name —
it's a recently added character we haven't added support for yet.

[Save with a different spelling]   [Contact support — we can enter it manually]
```

The support path has to be real. "Contact support" is only honest if support can actually store the value, which means an operator can move that column to `bucket`, or store the row through a path that does not derive the index.

**Where rule 1's two halves come from.** `fieldseal.first_unassigned(text)` returns the offending code point and its offset, in code points — the unit this section's own example counts. It is exported from the package root for exactly this (`docs/09` §7.1; G22, [#88](https://github.com/fieldseal-dev/fieldseal-spec/issues/88)), so no adapter needs to parse an error message to build the message above, and no adapter needs a second copy of the Unicode assignment table — a second copy that drifts is a silent lookup miss, not a wrong message. This adapter's `locate_unindexable` keeps its normalizer-aware probe rather than calling the accessor directly, and deliberately: the accessor answers `nfc-casefold-v1`'s refusal rule, while a column may declare a normalizer whose rule is narrower (`identity` refuses surrogates and accepts unassigned code points). Probing the declared normalizer is the general answer; the accessor is the right one for any adapter that knows it is on the `nfc-casefold-v1` path.

### 10.3 Choosing per column

The answer differs by column and a single rule is wrong somewhere:

- **A login email** — `refuse`. An account that exists and cannot be found by its own login is worse than a rejected signup, and the value is machine-shaped: a character outside the pin in an email address almost always means something upstream is broken.
- **A legal or display name** — `bucket`. Refusing a person's name is a hard failure for that person, and names are exactly where rare characters legitimately appear.

`bucket` requires `unindexable_override={"reason": ..., "approved_by": ..., "date": ...}`, refused at model-definition time (E-series check) if absent — the same ceremony spec §7.6 requires to relax the cardinality gate, and for the same reason: it is a per-column relaxation of a default-deny rule, so it should be a recorded act rather than a setting that gets copied.

### 10.4 What `bucket` costs, stated

The marker is a real index value derived under the column's own index key, so it is not distinguishable *as* the marker without that key. But the bucket is an equivalence class that can grow far past §7.4's expected `P × 2^(−b)`, so it is **distinguishable by frequency**: an observer who can read the index column sees one unusually popular value and can infer that those rows share "contains a character outside the pin". The class is also **growable by anyone who can write to the column**, which makes lookups against it progressively more expensive — bounded by re-verification cost, not by anything cryptographic. A column where either is unacceptable keeps `refuse`. The adapter documents both in its README rather than only here.
