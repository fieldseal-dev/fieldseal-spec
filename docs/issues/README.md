# Spec-gap issue drafts (G1–G20)

**Date:** 2026-08-08 · **Status:** all thirteen posted to the GitHub tracker on 2026-08-08; issue numbers align with gap numbers (G*n* = issue #*n*) for G1–G13 only — G14, filed 2026-08-22, is tracker #43, G15, filed 2026-08-23, is tracker #48, G16, filed 2026-08-25, is tracker #60, G17, filed 2026-08-25, is tracker #67, G18, filed 2026-08-26, is tracker #75, G19, filed 2026-08-26, is tracker #78, and G20, filed 2026-08-26, is tracker #80 — the intervening numbers having gone to pull requests. These files remain the canonical drafts; edits after posting belong in the tracker.

**As of 2026-08-09, eight are resolved** — G3, G6, G8, G9, G10, G11, G12, G13 — which is every gap flagged *no cryptographic review required*. The five that remain (G1, G2, G4, G5, G7) are exactly the five flagged **Yes** or **Partly**, so nothing further in this list can close by engineering judgment: they wait on the Phase 0 reviewers (`docs/16-reviewer-brief.md`). G11 is a partial close — its grammar is settled, its injectivity question belongs to G4.

**As of 2026-08-22, those five are *provisionally adopted* under Gate 0a and remain open.** The Phase 0 exit gate has been split (PRD §8) so that reviewer availability no longer blocks implementation. See [Provisional adoptions](#provisional-adoptions-gate-0a-2026-08-22) below for what each now says in the spec and what would close it. Nothing about the crypto-review column has been relaxed.

**G14 was added on 2026-08-22**, found in review of the TypeScript core rather than in the tech-spec suite: the optional context fields are unbounded, so the KDF `info` is unbounded, and platform HKDFs (Node at 1024 bytes, OpenSSL 3.0–3.5 at 32 KiB, .NET on Linux through OpenSSL) cap it. It needs no cryptographic review and is closable by engineering judgment, but should be seen by the Phase 0 reviewers first because it sizes the extension headroom of the §6.2 encoding Q4 asks about.

**G15 was added on 2026-08-23**, from the M2 report's divergence list (`docs/18` D-03, D-10, D-13, D-14) once the Python core had been brought to the same pins (PR #47): the `UNKNOWN_FORMAT_VERSION` set, `rotate()` on non-envelope input in `permissive`, the name of the §4.8 arming variable, and the Unicode version, folding variant, post-fold normalization and invalid-UTF-8 behavior of `nfc-casefold-v1`. Four parts in one issue because each is a one-paragraph normative change with the same closure shape; none needs cryptographic review. Two of its findings are new: 33 code points whose full case folding is not NFC-stable, and a bounded 28-letter / 34-mark divergence between the Unicode 16.0 table the Python core folds with and the 17.0 table the TypeScript core vendors.

**G16 was added on 2026-08-25**, from the consequences of closing G15 rather than from any core's behavior: neither core is wrong under the text as it now stands. Three parts. (A) A bytes-only index API cannot enforce §7.1's own lone-surrogate refusal — `TextEncoder` substitutes U+FFFD, so `encode("a\uD800b")` and `encode("a\uDC00b")` are the same five bytes, and the TypeScript core's error message points callers at exactly that conversion while the Python core has accepted `str` all along. (B) `encrypt` does not normalize and `blind_index` does, so a post-pin character stores but cannot be indexed, and §7.1's pointer to "§12 of `docs/12` and `docs/13`" for the refuse-vs-store-unfindable decision is dangling — those sections do not exist. (C) The pin has no currency policy, and bumping it today would silently pin the *draft*, because `Public/18.0.0/ucd/` 302-redirects to `Public/draft/ucd/` over plaintext HTTP and the generator follows redirects while logging the requested URL. **All four parts are decided.** Part D asked whether any of this belongs in the Gate 0b packet and answers no: Part A reads like a reviewer question and is not one (it decides a parameter type, not a construction), and the refusal rule's breadth turns on a UCD stability question rather than a cryptographic one. **G16 therefore has no reviewer dependency in either direction — the first issue since G13 that is entirely the project's own to close.** It also corrects the impact table in `internal/product-decision-indexing-edge-cases.md`: the 11,328-point block driving the "CJK personal names" case is **Seal Script**, a historic calligraphic script, and CJK Unified Ideographs gained one code point.

**G17 was added on 2026-08-25**, from an interface question the PR [#55](https://github.com/fieldseal-dev/fieldseal-spec/pull/55) review raised and nobody filed: `docs/09` §8.1 gives the `KeyProvider` signatures without saying who **owns** the byte strings they return, and §3.1/§3.2 prescribe erasure without saying what the core is entitled to erase. **The issue was filed with a defect claim that proved false and is withdrawn in place** — `api.ts:162`'s `ek.key.fill(0)` erases a copy, not the provider's buffer, because `#encryptionKey` validates and copies (`api.ts:182`); the regression test the issue asked for passed against unmodified code, which is how it was caught. What survives is narrower and real: the safety of two `.fill(0)` calls rests entirely on that copy, which exists for validation, is stated nowhere, was tested nowhere, and is one ordinary refactor from being removed — and a core in a language with mutable byte arrays and no immutability backstop reads §8.1 and gets no instruction either way. The Python core does neither, because `bytes` is immutable — which also makes two of the four erasure points `docs/09` §3 prescribes unperformable in that binding, a fact `docs/10` does not state even though §8.3 obliges every language document to. Nothing here is observable through the vector suite: buffer lifetime after a call produces no bytes to pin and no error to match, which is the argument for a `pinned_decisions` key rather than a vector family. **No cryptographic review, and — unlike G14 — no bearing on any Gate 0b question.**

**G18 was added on 2026-08-26**, from the first adapter meeting the core's public surface rather than from either core: `docs/09` §2 specifies a client that validates everything at construction and is immutable afterwards, and says nothing about reading any of it back. So `docs/12` §5's **E006** — a user-supplied `FIELDSEAL["CLIENT"]` whose index registry must exactly match the model declarations — could not be written, and shipped in PR [#73](https://github.com/fieldseal-dev/fieldseal-spec/pull/73) as a **W004 warning** that reports the gap instead. The two cores are not equally affected, and the worse one has no workaround: Python's `_indexes` is private by convention, while TypeScript's `#cfg` is a hard private field on a frozen instance, so a Prisma or TypeORM adapter cannot implement the check well *or* badly. The silence has already produced divergence in both layers — the two cores disagree about reflection generally (TypeScript exposes `readMode`, `writeSuite`, `allowedSuites` and `provisionalArmed`; Python exposes none of the four, its only public attribute being the `plaintext_reads` counter), and the two adapter designs answer the escape-hatch question opposite ways, `docs/13` §2 removing the `client` option outright and citing the Django check as its reason. The proposed rule is stated as a principle rather than a list — a client MUST be able to report every validated element that affects stored bytes, query results or read behaviour, in resolved form, through accessors that cannot mutate it, and MUST NOT expose its `KeyProvider`, cache or key material. **Deliberately no `pinned_decisions` key**, unlike G17: buffer lifetime was unobservable in principle, whereas an accessor's presence is directly testable, and a report key would legitimise a divergence this issue exists to end. **No cryptographic review, and no bearing on any Gate 0b question.**

**G19 was added on 2026-08-26**, from writing the Django adapter's §7.5 re-verification filter — the first gap this project has found in the *specification* rather than in a tech-spec document. §7.5 requires an implementation to "decrypt and compare **the actual values**" and never says under what equality. On any column declaring `nfc-casefold-v1`, a row stored as `Ada@Example.com` and queried as `ada@example.com` returns **0 rows** under byte comparison and **1 row** under normalized comparison; both are defensible readings and an adapter cannot ship §7.5 without picking. Two project documents already point opposite ways: `docs/12` §3.3 refuses `iexact` because "case folding belongs to the normalizer, not the query" — a promise that only holds under the normalized reading — while `docs/09` §7.2's bucket paragraph is phrased for the byte one. **The argument that decides it:** under byte comparison a folding normalizer enlarges every candidate set, coarsens the bucket, and buys no query capability, so it is worse than `identity` on exactly the columns §7.3 recommends it for — and canonical equivalence (`U+00E9` versus `e` + `U+0301`) has no sane answer at all, with no ORM lookup to refuse people towards. Proposed: compare `normalize(stored)` against `normalize(queried)` under the index's own normalizer, with adapters documenting that such a column has exactly **one** equality and MUST NOT offer a second. **Unlike G17 and G18 this one is vector-expressible**, and belongs there rather than in per-adapter tests, because two adapters resolving it differently is the cross-implementation failure the suite exists to catch. No cryptographic review — it defines an equality over already-decrypted plaintext, downstream of every cryptographic operation — and no bearing on any Gate 0b question.

**G20 was added on 2026-08-26**, from the PR #79 review round rather than from new code: the sweep that closed the `LIMIT` family (`get()`'s 21-candidate window, `qs[i]`, `earliest`/`latest` on verifying querysets) asked the same question — *what does the database answer from bytes the adapter never showed it?* — of `ORDER BY`, `GROUP BY` and `DISTINCT`. The specification already rules at the principle level (§7.10: `ORDER BY` → **No**) and §10.2 already contains both the rule and the exact throw sentence — for exactly one ORM, Prisma, written against one surveyed library's failure mode. The two shipped adapter designs read that silence in opposite directions: `docs/13` §5 throws, `adapters/django` serves the shape silently — measured, not assumed: `.order_by("email")` returns envelope-byte order; `.values("email").annotate(n=Count("pk"))` returns four groups of `n=1` where the truth is three groups with one `n=2`, two of them printing the identical key; `.earliest("email")` returns the wrong row. The `GROUP BY` case is the reason this is a gap rather than a documentation nit — wrong *numbers*, and §7.10's `GROUP BY`/`DISTINCT` row covers only the index sibling, not the ciphertext column every ORM compiles from the natural spelling. Proposed: an **All ORMs** bullet in §10.2's known-cases list, §7.10's row split (sibling: yes with the collision caveat; ciphertext column: **No**), the Django refusal design in `docs/12` (queryset refusals on every `FieldsealQuerySet`, obligations or none, plus checks for `Meta.ordering` and admin sortable columns), and the interception honesty in `docs/04` — ordering resolution has no field hook, so a plain-manager model ordering through a relation is a documented residue in the raw-SQL class. No vector obligations, no cryptographic review, no bearing on any Gate 0b question.

**G19 closed 2026-08-26**, the day it was filed, adopted as proposed — reading B. Spec §7.5 now states the equality it means: `normalize(stored_plaintext)` against `normalize(queried_value)`, under the normalizer declared for the index that produced the candidates, compared on the normalizer's output bytes — plus the adapter obligation the issue drafted: a non-`identity` column has exactly **one** equality, an adapter documents that a query for `ada@example.com` can return `Ada@Example.com`, and MUST NOT offer a second, differently-folded equality beside it. The three closure arguments are recorded in §7.5's justification paragraph: under a byte-exact reading a folding normalizer enlarges every candidate set and buys nothing (worse than declaring no transformation at all, on the email-like columns §7.2's example points folding at); the index's equivalence classes *are* normalization classes, so verification comparing under a different equality is a filter disagreeing with its own check; and canonical equivalence has no sane byte answer at all. **The vector obligation that kept it open is met**: suite `0.4.0-provisional` adds `normalizer-collapses-e-acute` — precomposed `U+00E9` against decomposed `e` + `U+0301`, the exact pair the issue and §7.5 cite — guarded twice in the generator: the two NFC-collapsible pairs (this one and `-precomposed`) are written as backslash-u escapes, and `_vectors` asserts every collision pair's preimages differ before deriving — identical preimages would satisfy the equality vacuously, and neither harness re-checks distinctness (the escape claim was false in this PR's first commit, caught by review; the assert is the guard that holds for every pair regardless of spelling). Both cores pass **145/145** with unchanged `pinned_decisions`; the case-variant half was already pinned by `normalizer-collapses-case` (suite 0.2.0), and the comparison rule itself is an adapter obligation held by per-adapter tests (`docs/14` §4 untouched, as the issue predicted). `docs/09` §7 and §7.2 carry the cross-references (the bucket paragraph now reads correctly under the rule: a bucket column's two unindexable values share one marker and are separated by exactly this comparison, under raw bytes since the normalizer refuses them); `docs/12` §3.2/§3.3 move from proposed to resolved phrasing; `docs/13` §3 gains the rule for the Prisma extension, naming `mode: "insensitive"`'s §5 rejection as the one-equality consequence. The Django adapter needed **no code change** — it shipped the rule as its prototype in PR #79 (`TestNormalizedEquality`).

**G20 closed 2026-08-26**, the day it was filed. Spec §10.2's known-cases list gains the **All ORMs** bullet (the Prisma `orderBy` sentence stays as its named instance) and §7.10's `GROUP BY`/`DISTINCT` row splits: the blind-index sibling keeps its yes-with-collisions caveat; the ciphertext column's row is **No**, with the materialize-then-compute fallback. **Closed as filed plus one addition:** aggregate and function expressions over a ciphertext column joined the refusal set after `aggregate(Min("age"))` over `{30, 40}` was measured returning `40` — the byte-wise minimum *envelope* decrypts cleanly to an arbitrary row's value and is presented as the minimum, with nothing raised — the one failure in the family that is both silent and *plausible*. The Django adapter implements the family as a second refusal class orthogonal to §7.5 verification: active on every `FieldsealQuerySet`, obligations or none, and **not lifted by `.candidates()`** — `order_by` (strings, relation paths, `F`/`OrderBy`/function expressions), `earliest`/`latest` (including the `Meta.get_latest_by` fallback, which never passes through `order_by()`), `distinct` (named fields, and argless over a `values()` projection naming an encrypted column, in either call order), expression references in `annotate`/`alias`/`aggregate`/`values`, and `values(enc).annotate(<aggregate>)` grouping. A bare `F("email")` annotation stays allowed — it only selects, and the converter decrypts what comes back. The two declaration doors the compiler applies directly get checks: **E009** (Error) for `Meta.ordering`/`get_latest_by`, **W005** (Warning) for an encrypted column the admin changelist would order by. The residue is documented rather than owned: ordering resolution has no field hook, so a plain-manager model ordering through a relation onto another model's encrypted column is not reachable — the raw-SQL class (`docs/04` §1). No vector obligations, no envelope byte, no derived value, no error code, no `pinned_decisions` key; both cores untouched. Django adapter 196 → 228 tests; the refusal tests were run against the pre-fix code to confirm they bite (20 of 32 fail there).

**G18 closed 2026-08-26**, the day it was filed. `docs/09` §2 gains a normative ***Configuration reflection*** clause: a constructed client MUST report back every validated element affecting stored bytes, query results or read behaviour — `read_mode`, `write_suite`, `allowed_suites`, the §4.8 arming state and the validated index declarations — in **resolved** form, through accessors that cannot mutate it, and MUST NOT expose its `KeyProvider`, cache or key material. **What was broken was a claim, not a mechanism:** §2 already said immutability "makes 'which config produced this ciphertext' answerable", and immutability is necessary for that but not sufficient — the sufficient half was never specified. The rule is stated as a principle rather than a field list because the `KeyProvider` carve-out is what makes it safe to state broadly. **Closed as filed with one addition, recorded rather than absorbed:** `ValidatedIndex`, `validate_index_declaration`/`validateIndexDeclaration` **and** `index_registry_key`/`indexRegistryKey` all became public, because a caller that can read a client's registry and cannot resolve its own declarations to the same form still cannot compare against it. Three runtime guarantees turned out to be load-bearing and none came from a type: the TypeScript `indexes` and `allowedSuites` accessors both copy (`ReadonlyMap`/`ReadonlySet` are erased, and each getter otherwise hands out the collection the value path consults), and `validateIndexDeclaration` now freezes what it returns (`readonly` is a compile-time claim; a cast could otherwise rewrite `truncateBits` on a live index). Python needed none — `MappingProxyType` over frozen dataclasses has no mutating methods at all, and `allowed_suites` was already a `frozenset`. **`allowedSuites` was missed on the first pass and caught in review:** it predates G18, so the new clause made an already-existing accessor non-conformant — the hazard of writing a rule for a surface that grew before it. `docs/12` §5 restores **E006** as an Error and **withdraws W004**, whose id is not reused and which had shipped with no test; the check now compares both directions, only one of which is loud. `docs/13` §2's no-`client`-option decision stands but its justification narrows to the design choice it is. **No `pinned_decisions` key and no `out_of_band` entry, deliberately unlike G17** — buffer lifetime was unobservable in principle, whereas an accessor's presence is testable per core, and `pinned_decisions` declares a choice a conformant core may make differently. No vector obligations, no envelope byte, no derived value, no error code. Both reports 144/144 with unchanged key sets; Python 294 → 298 tests, TypeScript 287 → 292, Django adapter 68 → 74. Implementing it also turned up a second defect the issue had not predicted: `FIELDSEAL["CLIENT"]` was silently switching off **E003**, because `build_client` returns a supplied client without ever assembling the registry, so the §7.4 band and §7.6 gate never ran against the models on that path. The E006 comparison resolves the model side anyway, which is what makes the gate reachable there; a refusal is reported under E003.

**G17 closed 2026-08-25 — and the defect it was filed on does not exist.** `docs/09` §8.1 now states that key material returned by `encryption_key`/`decryption_keys` is **provider-owned** (a core MUST NOT mutate or retain it, and MUST copy first if it wants something to erase) and that candidate reads do not count against §8.3's `max_uses`; §3 gains a preamble qualifying its four erasure steps by the binding's mutability and pointing at §8.3's honesty obligation; `docs/10` §5 states the two steps the Python core cannot perform; `docs/11` §5 states the `#encryptionKey` copy as the load-bearing mechanism it always was. **No line of either core's value path changed** — the rule codifies what both already do. Part A had claimed the TypeScript core erases the provider's own buffer; it erases a copy `#encryptionKey` makes while validating (`api.ts:182`), and the regression test the issue itself demanded is what established that, by passing against unmodified code. The surviving finding is that this invariant was stated nowhere and tested nowhere while the safety of two `.fill(0)` calls rested on it. Both cores gained provider-borrows-nothing tests and a `key-material-ownership` `pinned_decisions` key (docs/14 §4), which is the only executable form a buffer-lifetime requirement has; the Python harness also gained the required-key assertion the TypeScript one has carried since G15. Python 278 → 294 tests, TypeScript 281 → 287, both 144/144 with identical `pinned_decisions` key sets.

**G16 closed 2026-08-25** — all four parts, and the Unicode 18.0 bump is deliberately **not** among them. *Part A:* `docs/09` §7.1's note is now normative in the opposite direction from how it started — an index-derivation API **MUST accept the language's text type**, bytes still permitted through clause 5's strict decode. The obligation it replaces was unenforceable by construction (advice to a frame the core cannot inspect, where a missed call raises nothing and fails no test), and the TypeScript core had been countermanding it with an error message naming `TextEncoder` — the very conversion that substitutes U+FFFD. `blindIndex` now takes `string | Uint8Array`. The lone-surrogate refusal **could not become a vector**: `blind-index/` keys its input as hex bytes, an unpaired surrogate has no UTF-8 encoding, and widening the field to text would not help because Go string literals cannot hold a surrogate value and Rust's `String` is UTF-8 by invariant. It is the `out_of_band` entry `docs/09/7.1/lone-surrogate-refusal` instead, asserting not merely that both surrogates are refused but that they are refused **distinguishably**. *Part B:* new normative `docs/09` §7.2 — `on_unindexable = refuse | bucket`, marker `truncate(IDF(index_key, 0xFF ‖ "fieldseal-unindexable-v1"), b)`, whose leading `0xFF` is never valid UTF-8 so it cannot collide with any accepted value by construction rather than by luck, and which is *derived* rather than constant so it does not announce to a reader of the column which rows hold an out-of-pin character. `bucket` is gated on the same `{reason, approved_by, date}` ceremony §7.6 requires, and is a `ConfigurationError` on a normalizer that can never refuse. A design correction is recorded in §7.2 rather than substituted quietly: the query path needs **no** extra probe, because the marker is derived from normalization and a query for an unindexable value derives it unaided — the bucket is one more §7.4 collision class, not a new mechanism. The adapter obligation landed in `docs/12` §10 and `docs/13` §9, closing the dangling "§12" pointer this issue was partly filed about. *Part C:* `docs/09` §7.1 gains ***Pin currency (normative)*** — before the freeze the pin tracks the latest **released** Unicode version and moves **in place**; after the freeze the same move MUST mint `nfc-casefold-v2` and come with a planned re-index, so **the cost jumps at the freeze rather than rising with stored rows** and deferring the bump saves nothing. `tools/ucd-gen/generate.py` now refuses redirects and non-HTTPS hops and verifies that the URL which answered is the URL requested — a live trap, not a hypothetical: `Public/18.0.0/ucd/` 302-redirects to `Public/draft/ucd/` over plaintext HTTP, `urllib` followed both by default, and `download()` logged the URL it *asked for*, so bumping `VERSION` would have generated tables from a moving draft, labelled them `18.0.0`, and logged a fetch that never happened. New `tools/ucd-gen/test_generate.py` (five offline checks, no pytest, so a flake cannot mask a regression in the guards) runs ahead of regeneration in the `unicode-tables` job. **The 18.0 bump is not done and could not be**; it waits on the release. *Part D:* none of this goes to the Gate 0b reviewers — Part A *reads* cryptographic (a false match in a blind index) but decides a parameter type, changing no construction, derivation or stored byte, and the refusal rule's breadth turns on a UCD stability question for which a cryptographer is the wrong expert. **G16 therefore had no reviewer dependency in either direction — the first issue since G13 that was entirely the project's own to close.** Vector suite 0.2.0 → **0.3.0-provisional** (three `blind-index/` vectors); both cores 144/144. Landed as PR #61, which also ported the declaration-time gates the Python core turned out to enforce **none** of — no §7.4 band, no §7.6 cardinality gate, no skew, no override ceremony — although `docs/10` §4 had specified exactly that API all along; the implementation had drifted from its own binding document.

**G15 closed 2026-08-24.** Parts A, B and C as proposed plus three additions (§3.1's 111-byte floor on a future format version, and byte-exact comparison and the either-arms rule in §4.8); part D's item 4 closed the *other* way — `nfc-casefold-v1` gains a post-fold NFC, because the proposed composition was measured to leave eight assigned Greek code points failing to collide with their own uppercase spellings. Full reasoning and consequence sweep in `docs/07` §7.

## Provisional adoptions (Gate 0a, 2026-08-22)

**These are not closures and must not be read as any.** The Phase 0 exit gate is now split (PRD §8): Gate 0a permits implementation, Gate 0b — two credentialed reviewers — permits freezing. G1, G2, G4, G5 and G7 are the five gaps that cannot close by engineering judgment, and they remain **open on the tracker**. What changed on 2026-08-22 is only that each issue's *proposed direction* is now written into the spec as normative text carrying a **[PROVISIONAL]** marker, so that vectors and cores have something concrete to be built against.
